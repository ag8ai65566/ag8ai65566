### PP&E rollforward 為什麼被降級

原本規劃是用「期初 PP&E + 本期增添 − 折舊 = 期末 PP&E」反推 META 的單季 capex。
實際上這條式子含**處分、減損、匯率換算、重分類**四個未知數，而 10-Q 對這幾項的揭露
粒度不足以拆開。它可以當**一致性檢查**（差太多就是有問題），不能當**取得管道**
（拿它產生的數字餵進合計）。目前兩者都還沒做——降級的是野心，不是優先級。

## 2. 這一輪發現的三個 bug（都不是新寫的程式造成的）

### 2.1 一整張卡片從頁面上消失

引擎多了第三種 decision 狀態（`RULE_EVALUATED_ON_SUPERSEDED_PERIOD`），
renderer 仍然只認 `=== 'RULE_EVALUATED'` 和 `=== 'NO_DECISION'`。capex 兩邊都不符合，
於是**沒有被畫出來**——而它上方的總結照常寫著「13 條規則已評估」。

沒有任何東西失敗。頁面只是少了一張卡。

**修法不是補一個 case**，而是讓分桶窮盡：最後一桶接住所有前面沒接住的，並加測試
`every gauge the engine produced reaches the page`。計數來自引擎，所以光比對數字抓不到
這個錯，必須比對**畫出來的東西**。

### 2.2 頁面宣稱它有一個它明講自己沒有的能力

masthead 寫的是 `data.point_in_time ? '是' : '否'`。引擎給的是字串
`'NOT_IMPLEMENTED'`，而非空字串一律為真，所以頁面印出**「Point-in-time：是」**——
就在一段解釋 point-in-time 尚未實作的頁尾正上方。

狀態欄位不是布林值。把它當布林值用，錯誤方向永遠是**朝著誇大能力那一邊**。

### 2.3 護欄的正則從來沒有生效過

`/\b(建議|應該|值得)\s*(買進|加碼|…)/` —— JavaScript 的 `\b` 定義在 ASCII 詞字元上，
`建` 不是詞字元，所以 `\b建` **在字串開頭永遠不匹配**。
「建議加碼」四個字可以直接穿過那條專門用來擋它的規則。

看起來很嚴格、實際上什麼都沒擋，比沒有護欄更危險。

## 3. 一個判斷上的轉向：連坐 → 敏感度

第三輪的規則是「任何成分未對帳，整格不評估」。第四輪裁決指出這是過度保守，我同意，
但**理由不是「太嚴格不方便」**，而是它問錯了問題。

- 舊問題：有多少比例被驗證了？（META 佔金額 14.6%，所以覆蓋率 85.4%）
- 新問題：沒被驗證的那一份，**有沒有可能讓判定翻過門檻**？

實際測試：META 在 ±25% 內任意變動，環比落在 **0.83% ～ 18.73%**，全程為正，
規則判定始終是 `NOT_ROLLED_OVER`。**決策對未驗證部分不敏感，所以恢復評估。**

輸出刻意命名為 `SENSITIVITY_RANGE`，並在資料裡直接寫上「這不是信賴區間」。
沒有機率模型支撐的東西，不能長得像有。

同理，覆蓋率的三個數字在資料結構裡就帶著 `_naming_rule`：
**佔水位 15% 的成分，可能就是變動的全部。**覆蓋率永遠不是信心水準。

## 4. UI / 內容這一輪改了什麼

| 改動 | 為什麼 |
| --- | --- |
| 逃生鈴總結改寫 | 原文寫「還沒響」而完全沒提這是上一季的讀數。現在第一句就是「這不是最新的一季」，並說明差距卡在 META 的取得路徑 |
| 三層新鮮度做成三欄 | 重點是三個數字之間的**落差**，單一個「as of」日期不可能表達「管線才是慢的那一方」 |
| 已被超過的季度不再是綠色 | 卡片邊框與鈴的顏色改為古銅色。文字說「這是上一季的」而顏色說「綠燈」時，眼睛先贏 |
| 測試分類取代「59 tests passing」 | 總數聽起來像保證，卻沒說通過的是哪個問題。第五格（訊號驗證 0/0）刻意留空並置於版面上 |
| 「Since last run」區塊 | 快照歷史存在的意義要看得見。差異在引擎算，renderer 一個減法都不做 |
| 最右欄「來源有沒有更新」 | 數字變了不代表市場動了，也可能是同一生效日的資料被修訂或重讀。這兩件事在儀表板上長得一樣 |
| 「三個鏡頭」改寫 | 三條流程跑在同一批 SEC 與市場資料上。證據多樣性取決於**背後有幾個獨立出處**，不取決於跑了幾條流程 |
| 標普「距高點 0%」改寫 | 它就是 52 週最高點本身。寫成「0%」是把最重要的事實藏在一個看起來像沒事的數字裡 |
| 置頂導覽列 | 頁面已長到「往下捲到看見為止」變成導覽方式，而那會把警語埋在數字底下 |
| `npm run build` | Dashboard 曾落後引擎三個版本，因為「重新產生」是一串要記得的指令 |

## 6. 想跟審查者討論的四件事

### Q1 · ±25% 這個衝擊幅度，本身是不是又一個我自己拍的門檻？

敏感度測試解決了連坐問題，但 **±25% 是我選的**，沒有任何依據。
我在資料裡標明了它是假設、也標明沒有機率模型，但這仍然是「用一個未經驗證的參數
去解除另一個限制」。

可能的替代：用該發行人歷史單季變動的實際分佈來決定衝擊幅度。
問題是那等於用它自己的歷史當先驗，而 META 的歷史正是無法驗證的那一份。

**想問的是：在沒有可驗證歷史的情況下，敏感度測試的衝擊幅度應該怎麼定，
才不會變成又一個看起來嚴謹的自訂數字？**

### Q2 · `ECONOMIC_OUTLIER` 什麼都不封鎖，它到底該不該存在？

第三輪把它降為「僅提醒」是對的——0.25 那個門檻本來就沒有統計依據。
但現在的狀態是：系統發現一個異常、印在頁面上、然後**不會有任何後續**。

三個選項：
1. 建一個資料品質佇列，異常進佇列並要求人工裁決（真正的成本是要有人去看）
2. 維持現狀，但明說它只是「值得看一眼」而不是系統判斷
3. 刪掉——一個不導致任何行動的警告，長期只會訓練使用者忽略警告

我傾向 (1)，但只有在**確定有人會處理佇列**時才成立；否則 (3) 比 (2) 誠實。
**想問的是：一個沒有處理流程的警告機制，留著是資訊還是雜訊？**

### Q3 · 同一類 bug 這是第四次出現

三次是護欄掃到自己的免責聲明。這一次是狀態字串被當成布林值、
以及分桶不窮盡導致卡片消失。**共同結構是：某個地方把「有結構的狀態」壓成
「比較簡單的形狀」——字串壓成布林、多值壓成二值、資料壓成 HTML 字串。**

我這次的修法是逐個加測試，但這只擋住已經發生的那三個。
**想問的是：這是不是應該在型別層而不是測試層解決？**
（例如所有 status 欄位都必須經過一個 `renderStatus()`，該函式對未知值直接拋錯，
而不是讓每個使用點各自決定怎麼顯示。）

### Q4 · 「可稽核」已經很完整，「有效」還是零。這個比例本身是不是問題？

現在有 59 個測試、8 欄位溯源、五維狀態、三層新鮮度、概念契約、輸出契約。
**訊號驗證仍然是 0/16。**

我擔心的不是驗證還沒做——那是資料限制，誠實標示了。
我擔心的是：**這麼多層嚴謹的基礎建設，本身會不會讓使用者以為結論也同樣嚴謹？**
頁面上寫了「經統計驗證的訊號：0」，測試分類也把空的那一格畫出來了，
但整體觀感仍然是一個非常精密的系統。

**想問的是：當「工程嚴謹度」與「結論可信度」差距這麼大時，介面上還能做什麼，
才不會讓前者替後者背書？** 或者反過來說——是不是應該先停止增加基礎建設，
直到驗證層有第一個結果為止？
