## 1. 滯後比這個度量對嗎？

### 我做了什麼

原本用日曆天判斷新鮮度。問題是週日晚上跑，週五收盤會被算成「3 天前的舊資料」——
但那就是市場的當前狀態。所以改成兩件事：

```js
const PERIOD_DAYS = { 'business daily': 1, weekly: 7, monthly: 30, quarterly: 91 };

function dataState(series) {
  const end = effectiveEnd(series);                    // 季度資料用期間結束日，不用標記日
  const calendarAge = dayDiff(end, RUN_AT);
  const sessionAge = series.ds.measure_age_in === 'trading_sessions'
    ? tradingSessionsBetween(end, RUN_AT) : null;      // 市場資料用交易日計齡
  const age = sessionAge ?? calendarAge;
  const period = PERIOD_DAYS[series.ds.expected_frequency] ?? 1;
  const staleness_ratio = calendarAge / period;        // ← 這一行是問題所在
  const limit = sessionAge === null ? sla : Math.max(3, Math.round(sla * 5 / 7));
  if (age <= lat + (sessionAge === null ? 1 : 0)) return 'CURRENT';
  if (age <= limit)     return 'LAGGED_BY_DESIGN';
  if (age <= limit * 2) return 'OVERDUE';
  return 'STALE';
}
```

實際效果：

| 指標 | 日曆天 | 發布週期 | 滯後比 | 判定 |
| --- | --- | --- | --- | --- |
| 準備金（週） | 5 | 7 | **0.71** | LAGGED_BY_DESIGN |
| 巴菲特（季） | 132 | 91 | **1.45** | LAGGED_BY_DESIGN |
| capex（季） | 102 | 91 | **1.12** | LAGGED_BY_DESIGN |
| 融資餘額（月） | 71 | 30 | **2.37** | OVERDUE |

### 我的疑慮

滯後比等於在說：**「只要沒超過一個發布週期，就算新鮮。」**

這對**平滑、慢速演化**的序列成立。但對**慢速卻會突變**的序列可能危險：

> capex 是季頻。如果雲廠商在 4 月法說會上口頭下修下季指引，
> 那個訊息在 4 月就進了市場價格，但我的儀表板要到 7 月底的 10-Q 才會知道。
> **我會有整整一季顯示綠燈，而市場早就轉向了。**

滯後比會告訴我「1.12 個週期，正常」——**它在結構性地看不見的時候，回報「一切正常」。**

### 問題

- **Q1a** 滯後比該不該依「該序列的變異速度」加權，而不是純用發布頻率？
  （例如：一個平常 QoQ 波動 ±3% 的序列，落後一季的風險，遠低於一個常態 ±25% 的序列。
  這裡的 capex QoQ 實際區間是 **−0.6% 到 +22.9%**。）
- **Q1b** 對「發布週期長、但期間內可能有場外資訊（法說會、指引）」的指標，
  是否需要一個獨立的 `information_may_be_stale_despite_ratio` 旗標？
- **Q1c** 交易日計齡我沒有處理美股假日，只處理週末。這在感恩節／聖誕節那幾週會低估年齡 1–2 天。
  值得為此引入假日行事曆嗎，還是這個誤差可以接受？

## 3. 合理性閘門的門檻是我拍的

### 我做了什麼

建財報管線時，SanDisk 的資產週轉率算出來只有 **0.161**
（年化營收 $28.3B ÷ 總資產 $175.88B）。對這門生意不合理。
數字內部一致（資產 ≈ 負債 + 權益）且跨四季穩定，所以不是抓取錯誤——
但我無法只用 XBRL 判斷它是否符合我的假設（可能是合併合資廠資產、實體範圍不符、或 tag 語意不同）。

於是加了閘門：

```js
plausibility: (() => {
  const flags = [];
  const turnover = assets && rev ? (rev.val * 4) / assets.val : null;
  if (turnover !== null && turnover < 0.25) {          // ← 0.25 從哪來的？我拍的
    flags.push({ metric: 'asset_turnover', value: turnover,
      issue: '資產週轉率異常低，可能是合併合資廠資產、實體範圍不符，或 tag 語意不同。',
      affects: ['roe_annualised_pct'], action: 'VERIFY_AGAINST_FILING' });
  }
  const gm = gmAligned ? gp.val / rev.val : null;
  if (gm !== null && (gm > 0.95 || gm < 0)) { /* 0.95 也是我拍的 */ }
  if (eq && assets && eq.val > assets.val) { /* 這條是恆等式，有依據 */ }
  return { flags, status: flags.length ? 'FLAGGED' : 'PASS' };
})()
```

### 我的疑慮

**這可能是同一個錯誤的重演。** 兩輪之前我為準備金速度寫了「四週跌 3% 就黃燈」，
實測落在 **p21.8**——根本不算快，純粹是我發明的數字製造假警報。當時的修法是
改用**該序列自己的百分位**（底部十分位）。

現在的 `0.25` 和 `0.95` 是一模一樣的做法：**憑感覺挑的絕對門檻。**

差別在於：
- 準備金有 40 年歷史可以算百分位。
- **資產週轉率的「正常範圍」是跨產業的**，半導體和軟體差一個數量級。
  我沒有產業別的分布資料。

### 問題

- **Q3a** 對這種**沒有自身歷史可比、只有跨產業常識**的合理性檢查，
  正確做法是什麼？（用同業比較？用該公司自己的歷史區間？還是根本不該自動化，改成人工白名單？）
- **Q3b** 資產週轉率這條，用**該公司自己過去 8 季的區間**當基準，
  是不是比跨產業絕對值更好？（缺點：它不會抓到「從第一天就抓錯 tag」的情況。）
- **Q3c** 一個標了 FLAGGED 但實際上是誤報的閘門，長期會不會訓練使用者忽略所有 flag？
  （狼來了問題。目前 2 檔持股裡有 1 檔被 flag。）

## 4. 合理性 FLAGGED 的公司，賺錢能力還能給 `proven` 嗎？

### 現況

Serenity 的 Buffett 閘門規則是：**每個欄位預設 `unverified`，只有引用證據才能升級。**
我接上財報後，兩檔持股的結果：

| | MU | SNDK |
| --- | --- | --- |
| 賺錢能力 | **`proven`** | **`proven`** |
| 護城河 | `unverified` | `unverified` |
| 客戶替換風險 | `unverified` | `unverified` |
| 合理性檢查 | **PASS** | **⚠️ FLAGGED**（資產週轉率） |
| 結論 | 研究地图 | 研究地图 |

升級條件的程式碼：

```js
const haveProfit   = m.revenue_usd !== null && m.net_income_usd !== null;
const growing      = (m.revenue_yoy_pct ?? -1) > 0;
const cashPositive = (m.free_cash_flow_usd ?? -1) > 0;
gate.profitability = haveProfit && growing && cashPositive
  ? { value: 'proven', evidence: [...], citations: [...] }   // ← 完全沒看 plausibility
  : { value: 'unverified', reason: '...' };
```

實際數字（SNDK，期間 2026-06-30，申報 2026-08-06）：
營收 $7.08B（年增 +30.63%）、淨利 $1.91B、淨利率 27.02%、FCF $1.12B、
毛利率**未揭露**（SanDisk 未 tag `GrossProfit`）。

### 我的疑慮

**一家資產負債表有疑慮的公司，賺錢能力還能算 `proven` 嗎？**

我的直覺是**閘門應該連動**：任一合理性 flag 就把所有依賴該報表的欄位降級。
但我沒實作，因為想不清楚三件事：

1. **降到哪一級？** 直接回 `unverified` 太粗暴——營收和 FCF 那幾個數字本身沒被 flag，
   被 flag 的是資產週轉率（影響 ROE）。
2. **會不會過度傳染？** 資產負債表有疑慮，不代表損益表有疑慮。
   一個 flag 拖垮整份財報，可能讓系統過度保守到沒用。
3. **需不需要「部分驗證」這一級？** 例如 `proven_income_statement_only`。
   但增加狀態值會讓 schema 複雜化，而上一輪裁決警告過不要過度工程化。

### 問題

- **Q4a** 閘門該不該連動？如果該，**傳染規則怎麼定**——
  按報表分（損益表 flag 才影響獲利欄位）還是一律降級？
- **Q4b** `proven` 這個詞本身是不是太強？來源 skill 的原文用的是
  `improving / proven`，我直接沿用了。給定我只有**一季**資料、沒有多年紀錄，
  `proven` 是否應該保留給有連續數年紀錄的情況？
- **Q4c** SNDK 的毛利率完全缺（公司未 tag `GrossProfit`）。
  在少一個關鍵欄位的情況下判 `proven`，是否本身就不該成立？

## 5. 「看起來嚴謹」本身是不是新的風險？（最想要答案的一題）

### 這套東西現在長什麼樣

- 27 個自動化測試全綠
- 每個數字有 8 欄位來源鏈（來源／權威／生效日／抓取時間／轉換／版本／commit／hash）
- 原始回應存檔加 sha256
- 五維狀態模型
- 引用到 SEC accession number
- 相關係數 0.766、百分位 p3、資產週轉率 0.161——**全部精確到小數點**

**但是：**

- **`signal_validation` 全部 16 格 = `UNTESTED`**
- 沒有任何一條門檻做過回測或樣本外檢驗
- 沒有 point-in-time 資料，**結構上不可能回測**（FRED 只給最新修訂版）
- 預測帳本只有 3 筆，**而且是我自己寫的**，其中 2 筆是
  「現狀會維持」型（HY OAS 維持 <4%、準備金不跌破 2.5兆）——
  **這種預測幾乎穩對，等於在製造一個假的成功紀錄**

### 我的疑慮

之前這套系統**明顯不完整**，所以你不會過度信任它。
現在它**看起來很專業**——但預測能力**完全沒有改變**（都是零）。

**我把可信度的「外觀」提升了，卻沒有提升可信度本身。**
這在心理上可能比之前更危險。

我在 UI 上試過的緩解措施：
- 每格都印 `UNTESTED`
- 頁面上方有「訊號驗證：0 VALIDATED」的計數
- 底部免責聲明說明門檻來自一位公開評論者

**但我不相信這些有用。** 一個佈滿 hash、accession number、百分位的頁面，
底下一行小字說「未經驗證」——**沒有人會真的把那行字當回事**，包括我自己。

### 問題

- **Q5a** 這是真問題還是我想太多？有沒有實證研究說明
  「精確度的呈現」如何影響使用者對「準確度」的判斷？
- **Q5b** 如果是真問題，**UI 上有什麼真正有效的做法**？
  我想過的（都不滿意）：把未驗證的數字**故意模糊化**顯示、
  強制先看驗證狀態才能展開數字、把所有數字改成區間而非點估計。
- **Q5c** **極端選項：在有回測之前，是不是根本不該顯示精確數字？**
  例如準備金只顯示「充足／吃緊／枯竭」，不顯示 2.993 兆。
  這會犧牲可追溯性（審查上一輪的核心要求），兩者衝突時該怎麼取捨？
- **Q5d** 預測帳本那 3 筆，我自己寫的、2 筆是現狀維持型——
  **這比沒有帳本更糟嗎？** 該不該作廢重寫成只收「會變化」型的預測？

## 7. 我沒問但可能該問的（請告訴我哪一項比上面五題更嚴重）

寫這份文件時我意識到七件事，它們都沒進上面的五題。
**如果你認為其中任何一項比我問的五題更重要，請直接說，並優先回答那一項。**

**A. 我把「二階導」實作成了年增率。**
狠人的原話是**「資本開支的二階導數，也就是環比增速」**。我的主判用的是 **YoY**，
理由是這四家的 QoQ 有明顯季節性（Q1 例行走弱：2025Q1 −0.6%、2026Q1 +9.37%），
單看 QoQ 會週期性誤報「見頂」。我在程式與 UI 都標了 `implementation_divergence`，
但**這仍然是把他的訊號換成了另一個訊號**。
→ 這個偏離是否讓開關三失效？季節性調整（例如 YoY of QoQ）是不是更忠實的做法？

**B. 我從未驗證過差分還原的正確性。**
10-Q 報年初至今累計，我用相鄰累計相減還原單季。MSFT 的數字看起來合理，
但我**從未拿任何一季的差分結果去對照公司自己新聞稿公布的單季數字**。
如果差分邏輯有錯，開關三的 QoQ 就是錯的（YoY 剛好不受影響，見 §6）。
→ 這是不是應該在做任何其他事之前先驗證？

**C. `point_in_time_capable: true` 是一個沒被行使過的宣稱。**
SEC 那條我存了 `filed`，並在 registry 標記可做 point-in-time。
但系統**從來沒有真的跑過一次 as-of 查詢**。這個能力是宣稱，不是驗證過的事實。

**D. 買賣訊號的護欄是我自己寫的 regex。**
```js
/STRONG\s+(BUY|SELL)/i, /\b(建議|應該)\s*(買進|買入|賣出|加碼|減碼|清倉|出清)/,
/目標價\s*[:：$＄\d]/, /price\s+target\s*[:：$\d]/i
```
一個模型要繞過這些太容易了（「這個位置的風險報酬比很有吸引力」完全不會被攔）。
→ lint 是正確的控制手段嗎，還是需要結構性的做法（例如輸出 schema 根本不含建議欄位）？

**E. 三個鏡頭可能沒有我宣稱的那麼獨立。**
我一直說「三個鏡頭刻意偏見不同」。但 `serenity-method` 和 `equity-research`
**都是基本面導向**，而我現在把財報接上之後，兩者會讀**同一份 SEC 資料**。
真正獨立的可能只有「狠人的部位／流動性視角」對上「基本面視角」——也就是**兩個**，不是三個。
→ 我是不是在誇大 diversity？

**F. 儀表板沒有任何「跟上次比」的能力。**
沒有歷史存檔，所以使用者無法看出準備金是在流失還是回填，
只能讀 velocity 欄位。這跟 Q1 的「結構性看不見」是同一個問題的兩面。

**G. 跨語言的術語漂移風險。**
來源框架是中文 YouTube 逐字稿，程式與文件是英文，儀表板是中文。
`環比`/`同比` → QoQ/YoY 我確認過是對的，但 `二階導` 就出了問題（見 A）。
→ 是否需要一個術語對照表當作正式產出物？
