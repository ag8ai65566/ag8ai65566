# 實驗模式：把「我覺得 0.45 比較好」變成量出來的結果

**素材庫分頁 → 實驗（固定 seed 掃參數）**

---

## 為什麼要有這個

這個 app 講的所有「最佳參數」—— 重繪 0.4～0.6、LoRA 強度 0.8、
弱 tag 要加到 1.2 —— **目前全部都是推測**。不是推理很爛，而是推理就是它的全部：
一張圖都沒生成過，所以那些數字是**穿著設定外衣的假說**。

外部審查講得更直接：**在 benchmark 出現之前，繼續堆 prompt 規則的邊際價值很低。**
它是對的。所以這裡做的是「把假說變成結果」的最小機器：

```
選要掃什麼 → 每個組合都跑「同一批 seed」 → 並排看 → 蓋住設定盲測 → 讀出勝率
```

---

## 三個設計重點

### 1. 每個變體跑**同一批 seed**

這是整件事的地基。如果每個變體各自抽 seed，那量到的是骰子不是參數 ——
**擴散模型的 seed 之間的差異，通常比你想找的效果還大**。

所以所有變體共用同一份 seed 清單。兩個變體之間的差別，就是那個參數。

### 2. 來源記錄用**內容雜湊**，不是檔名

每個實驗都會記下：

- checkpoint 的 **SHA256**（不是檔名 —— 檔名會被重複使用）
- 每個 LoRA 的 SHA256
- ComfyUI 的 commit、這個 app 的 commit
- 完整的 seed 清單、每個變體的參數

**一個你三週後無法歸因到確切設定的結果，是一個你無法拿來做決定的結果。**

（大檔案的雜湊有快取，鍵包含檔案大小與修改時間 —— 因為「同一個檔名換了權重」
正是這個機制要抓的事。）

### 3. 盲測，而且**「好看」和「像本人」分開算**

投票時**設定是蓋住的**，投完才揭曉。左右兩張誰先出現也是隨機的（避免位置偏誤）。

評分項目有五個，各自獨立計分：

| 項目 | 問題 |
| --- | --- |
| likeness | 比較像本人（身份、髮色、瞳色、髮型） |
| costume | 服裝比較對（配件、顏色、細節） |
| anatomy | 手腳／身體比較沒壞 |
| adherence | 比較符合提詞 |
| beauty | 單純比較好看 |

**漂亮但不像 Suisei 的圖，不該在「像不像」這項贏。** 這兩個混成一個分數，
整個優化方向就會被帶偏 —— 所以它們永遠不會被平均在一起。

## 怎麼用

1. 先在**圖片分頁**把一組**你已經跑得起來**的設定調好（提詞、底模、LoRA…）
2. 到**素材庫分頁 → 實驗 → 展開 → 「用目前圖片分頁的設定開一個實驗」**
3. 在要掃的軸填值，逗號分隔（例：`0.6, 0.8, 1.0`），不掃的留空
4. 看預覽：**幾組 × 幾個 seed = 幾張圖**，還有粗估時間
5. 「建立並排入佇列」→「排入佇列開始跑」
6. 跑完回來看 contact sheet（一列一個變體，每列同樣的 seed）
7. 選盲測項目 → 開始盲測 → 投票 → 看排名

可以掃的軸：**底模、LoRA 強度、重繪強度、CFG、步數、官方風格偏移、
畫師權重、sampler**。每個軸旁邊寫了它實際會改變什麼。

上限 **400 張圖**、每組最多 16 個 seed。超過會在**還沒花掉任何 GPU 時間之前**
就告訴你，並建議你減少軸或值。

---

## 建議先跑哪幾個

按「回答的問題有多重要」排：

| 實驗 | 掃什麼 | 回答什麼 |
| --- | --- | --- |
| **LoRA 強度** | `0.6, 0.7, 0.8, 0.9, 1.0` | 作者範例的 0.8 對你的 checkpoint 是不是最好 |
| **重繪強度**（要先放參考圖） | `0.35, 0.45, 0.55, 0.65` | 我文件裡寫的 0.4～0.6 到底對不對 |
| **官方風格偏移** | `0, 1.15, 1.25, 1.35` | `official art` ＋加權服裝 tag 真的有讓角色更像嗎 |
| **畫師權重** | `0, 0.8, 1.0, 1.2` | 掛原畫師到底是幫忙還是扯後腿（我只證明了「不是可靠的身份 token」） |
| **底模** | `noobai, illustrious, pony…` | 哪一支對你要畫的角色最準 |

每個都建議 **4～8 個 seed**。少於 4 個結論不穩，多於 8 個邊際效益遞減。

**票數少於 10 次比較時，排名會標「先別當結論」。**

## 我驗過什麼

| 驗過 | 結果 |
| --- | --- |
| 矩陣展開（乘積、去重、忽略未知軸、上限截斷） | 單元測試 |
| **每個變體真的跑同一批 seed** | 端對端，對假 ComfyUI 實跑 8 個工作驗證 |
| 每個工作真的帶自己的軸值 | 同上 |
| 配對兩邊 seed 相同、變體不同 | 端對端 |
| 投過的組合不再出現、左右隨機 | 單元測試 |
| **likeness 的票不會算進 beauty** | 端對端 |
| 雜湊快取的鍵含大小與 mtime（換權重會重算） | 單元測試 |
| 重複執行同一個實驗被拒絕 | 端對端 |
| 建立→預覽→上限警告→排入→盲測介面 | Chromium 實機 |

**沒驗過的**：實際生成的圖長怎樣。這個容器沒有 GPU ——
**而這正是這個功能存在的原因**：那些數字要在你的機器上才量得出來。

跑完之後，`docs/prompt-weights.md` 和 `docs/character-packs.md` 裡
所有標成 **HEURISTIC** 的東西，你都可以自己換成 **PROJECT-MEASURED**。
