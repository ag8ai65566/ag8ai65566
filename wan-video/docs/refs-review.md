## 1. 這次要解決的問題

使用者說：「圖載好了，因為數量眾多所以你先用最權威的圖源來做就好，
我放在 `C:\anim\wan-video\Holo pic\Hololive_Ultimate_Archive\01_官方角色全身立繪_最重要`」。

三件事因此成立：

1. **圖在他自己的機器上，而這個 app 也跑在同一台機器上。**
   原本只有「上傳檔案／zip」一條路，那是為了遠端部署設計的，
   在本機情境下等於逼使用者用檔案選取視窗點幾百個檔案。
2. **那個資料夾是中文命名的。** 原本的比對只認羅馬字和日文假名，
   中文名字的分數是 **0** —— 整包圖一張都對不到。
3. **「01_官方角色全身立繪」是最權威的圖源**，也就是最該優先接進來的。
   官方立繪正是 img2img／ControlNet 最有用的輸入。

## 2. 中文名字：資料來源

**沒有一個名字是我翻的。**

```
GET zh.wikipedia.org/w/api.php?action=parse&page=Hololive production
    &prop=text&variant=zh-tw
GET （同上）&variant=zh-cn
```

同一篇條目讀兩次，讓 MediaWiki 自己的字體轉換器產出繁體與簡體兩種寫法，
再從成員表格（`<tr>` → 儲存格）裡把「中文名」欄位和「日文名／羅馬字」欄位配對。
73 位對上這個專案角色包裡的 key。

三位成員表格裡沒有的（Roboco-san、A-Chan、Harusaki Nodoka）取自同一篇條目的
內文與 `link-ja` 模板。

**Watson Amelia 是特例**：兩個變體給的是不同的**譯名**而不是不同字體
（`華生·艾米莉亞` vs `沃森·阿米莉亞`），所以三種寫法都收 —— 檔案可能用任何一種。

**兩位刻意不收**：

| 成員 | 為什麼 |
|---|---|
| AZKi | 名字在中文裡也是拉丁字母，現有的羅馬字比對已經涵蓋 |
| Pekomama（ぺこらマミー） | zh.wikipedia 沒有條目，社群譯名不只一種。猜不如不猜 |

這兩個寫進 `NO_ZH_NAME` 並且有測試斷言「缺的就是這兩個，而且每一個都有理由」，
所以這是「宣告過的缺口」不是「忘了做」。

### 中途丟掉的一個做法（值得審查者知道）

第一版只拿到簡體，於是我想用「同時有繁簡的成員」去**推導**一張簡→繁字元對照表，
再拿去補其他成員。59 組字元對照推出來之後發現裡面有三組是錯的：
`沃/華`、`森/生`、`阿/艾` —— 全部來自 Watson Amelia 那一列，
因為那兩個來源用的是**不同譯名**不是不同字體。留著會汙染每一個含這些字的名字。

後來重試 API 成功拿到 zh-tw 之後，這整套推導就整個丟掉了 ——
**兩種寫法都直接從來源拿，不推導。** 現在的檔案裡沒有任何推導出來的名字。

## 3. 比對邏輯的兩個修正

### 3.1 中文名改成「連續子字串」，不是「每個字」

原本 CJK 是拆成單字比對（因為 Han 沒有空格）。這個做法對四個字的名字還好，
對兩個字的名字是災難：

```
`律可` 拆成 ['律', '可']
`可律的圖.png` 拆成 ['可','律','的','圖']
→ 兩個字都在裡面 → 100% 命中
```

**順序正是名字和巧合的差別。** Han 沒有空格，所以子字串本身就是詞界：
`星街彗星` 必須是那四個字、照那個順序出現。

部分命中仍然算分（`星街すいせい` 對 `星街彗星` 會拿到共同姓氏的分數），
但低於 MIN_SCORE 0.62 就什麼都不決定。

### 3.2 檔名認不出來就往上找資料夾

整理好的圖庫長這樣：

```
01_官方角色全身立繪_最重要/
  星街彗星/
    01.png          ← 檔名本身什麼都沒說
```

所以：**先比檔名**（最精確），認不出來才**由近而遠**往上找資料夾。

**沒有**把整條路徑合成一袋字去比。那樣的話：
最上層資料夾如果剛好叫某位成員的名字，底下每一張圖都會被汙染；
巢狀的「和某某某合作」資料夾也會蓋過檔名。

## 4. 就地索引（預設不搬也不複製）

匯入預設**只記住檔案在哪**，不把它複製進 app 的資料夾。

**為什麼**：

- 一包官方立繪動輒好幾 GB，複製等於白白多佔一份
- 那是**使用者自己的**資料夾。一個會偷偷重新整理你資料夾的工具，
  沒有人會用第二次
- 複製會讓「真相」分岔：在圖庫裡改個檔名，複製那份還是舊的

**代價，以及怎麼處理**：

| 情況 | 行為 |
|---|---|
| 圖庫被搬走／改名 | `load()` 會丟掉檔案已經不在的參考 → 從清單消失，而不是留下一堆點不開的破圖 |
| 重掃同一個資料夾 | 身分是**絕對路徑**不是內容雜湊，所以認得出是舊的，不會變兩份 |
| 同一張圖存在兩個路徑 | 會被當成兩張。這是這個模式的已知取捨 |
| 刪掉一張連結的參考 | 只從索引忘掉，**不刪使用者的檔案** |
| 重新指定角色 | 只改標籤，**不搬動使用者資料夾裡的檔案** |

**身分為什麼不是內容雜湊**：算雜湊要把整個圖庫每一個 byte 讀一遍，
而那正好是這個模式存在的理由（避免整包讀寫）。上傳路徑仍然用內容雜湊，
因為那邊 bytes 本來就在記憶體裡了。

`copy: true` 保留給隨身碟、或等一下就要刪掉的暫存資料夾。

## 5. 先掃描，再匯入

匯入之前一定先跑一次乾掃：

- **只讀檔名和資料夾名**，不讀任何一個 byte，不寫任何東西
- 回報：掃到幾張、多大、幾張對到角色、對到幾位、
  **幾張是靠資料夾名字認出來的**、以及**對不到的實際檔名**

最後那項是重點。這個比對器**從來沒看過使用者那個圖庫的命名慣例**，
所以唯一誠實的做法是先把答案給他看。而「對不到的長什麼樣」是他唯一能拿來
判斷的東西 —— 也是我下次要修名字表時唯一該看的東西（拿真實資料修，不是猜）。

## 6. 安全

新增的兩個端點會讀使用者給的本機路徑。這個 app 的定位本來就是**本機執行**
（它會啟動 ComfyUI、寫模型檔、跑 git pull），所以讀本機路徑不是新的權限層級。
即使如此：

- 只收 `.png/.jpg/.jpeg/.webp/.bmp`
- 單檔 40MB 上限、單次 20,000 檔上限
- **不跟隨 symlink**
- **從不刪除、從不移動**來源檔案
- 服務檔案的路由 `GET /api/refs/file/{pack}/{name}` **只服務索引裡有的東西** ——
  它拿 `(pack, name)` 去索引查路徑，所以索引不知道的路徑一律拿不到。
  （不是拿使用者給的路徑直接去讀。）

前一輪在這一塊修過一個**真的**路徑穿越 bug：`_safe()` 原本只把非法字元換掉，
但 `.` 是合法檔名字元，所以 `..` 整個活了下來，而 pack id 是從網址來的。
現在任何「只有點」的路徑元件會被換成 `_`。

## 7. 驗了什麼

Python 2,713 項、stub-DOM 42 項、真 Chromium 162 項，全過。

這次新增的關鍵斷言：

| 驗的東西 | 怎麼驗 |
|---|---|
| 中文名比對（繁簡各一組，12 種寫法） | 全部落在正確的成員 |
| 兩個字的名字不會亂 match | `可律的圖.png` 正確地誰都不對 |
| 資料夾名字比對 | `01_官方角色全身立繪_最重要/星街彗星/01.png` → hoshimachi-suisei |
| **掃描不動任何檔案** | 掃完之後比對整個來源資料夾的檔案清單，一模一樣 |
| **匯入不搬不複製** | 來源清單不變，且 `data/refs/` 裡沒有任何新的 png |
| 圖庫被搬走 | 那些參考自動從清單消失 |
| 刪掉連結的參考 | 索引忘掉它，來源檔案還在 |
| 重掃同一個資料夾 | 5 張全部認出是舊的，總數還是 5 |
| 複製模式 | bytes 真的複製進來，而且不是連結 |
| 連結的圖真的服務得出來 | Chromium 實機 fetch，200 |
| 「為什麼跟設定圖不像」會指向已匯入的圖 | Chromium 實機 |

**沒驗的**：

- **真實的那包圖庫。** 我沒有那些檔案，也不知道它裡面實際的檔名長什麼樣。
  上面所有比對都是對著我自己造的 fixture 跑的。**這是最大的未知數** ——
  所以才做「先掃描」，讓真實資料自己講話。
- **一張圖都沒生成過。** 這台機器沒有 GPU。所以「重繪強度 0.45 是不是最好的值」、
  「官方立繪當 ControlNet 是不是比當 img2img 來源好」，都還是推論。
- **用圖片內容分類**（例如跑 CLIP 或 tagger 去認角色）完全沒做。
  只靠名字。這是刻意的：名字認不出來就承認認不出來，比認錯人好。
  但如果審查者認為內容分類值得做，我想聽理由。

## 8. 想請審查者特別看的幾點

1. **子字串比對的門檻。** MIN_SCORE 0.62 是沿用原本羅馬字比對的值。
   中文名字改成子字串之後，這個門檻還合適嗎？
   （現在部分命中的分數是「最長共同子字串長度 ÷ 名字長度」。）

2. **「檔名優先、再往上找資料夾」的順序。** 有沒有反例是資料夾比檔名可信？
   例如檔案叫 `with 星街彗星.png` 放在 `兔田佩克拉/` 底下 —— 現在會判成星街。

3. **就地索引的失效模式。** 我想到的都寫在第 4 節了。還有什麼？
   （Windows 的路徑大小寫？網路磁碟機？OneDrive 的 placeholder 檔案？）

4. **zh.wikipedia 當作名字來源夠不夠。** 條目會被編輯，譯名也可能不是社群常用的
   那個。有沒有更適合的來源？

5. **20,000 檔的上限和 40MB 的單檔上限**是拍的。有更好的定法嗎？
